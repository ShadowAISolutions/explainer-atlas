Yes, Probably. No, Definitely.

A Bloom filter answers one question in two different voices. When it says no, it is certain. When it says yes, it is guessing — and you get to choose, in advance and exactly, how often it guesses wrong.

A Bloom filter is a bit array and a handful of hash functions, and nothing else. To record that you have seen an id, you hash it k different ways, treat each hash as a position in the array, and set those k bits to one. To ask whether you have seen an id, you hash it the same k ways and look. If any of those bits is zero, you have definitely never inserted it. If all of them are one, you have probably inserted it — or you have been unlucky.

That asymmetry is the whole device. A no is a proof: inserting the id would have set that bit, and the bit is not set, so the insertion never happened. A yes is only circumstantial: every bit it checked was already lit, but they could have been lit by other ids. There is no way to tell the two cases apart, because the array has no memory of which id lit which bit.

What it costs

Nothing here stores an id. Thirty-two ids at four bits each is 128 bits — sixteen bytes, for a structure that would take hundreds as a hash set, and the saving grows with the length of the keys, because a Bloom filter does not care how long they are. What you give up is exactness in one direction only, and you can price that exactly.

After inserting n ids into m bits with k hash functions, each particular bit has been left alone by every one of the kn bit-settings with probability (1 − 1/m) raised to the kn. A probe of an id that was never inserted reports present when all k of its bits happen to be lit:

false positive rate = (1 − (1 − 1/m)^(kn))^k
≈ (1 − e^(−kn/m))^k

The exponential version is the one usually quoted, and it is an approximation: at four bits per id with six hash functions it overstates the true rate by about four per cent. The page asserts the exact form and treats the approximation as what it is.

Why more hashing can hurt

Raising k cuts both ways. Each extra hash function is another bit a false positive has to get lucky on, which pushes the rate down. But each extra hash function also lights another bit per insertion, which fills the array faster and pushes the rate up. The two effects cross, and the crossing point is at

k* = (m/n) · ln 2

which is the k that leaves the array exactly half full. At that setting the rate collapses to one half raised to the power k*, or about 0.6185 raised to the power of the bits per id — so every extra bit per id multiplies the error rate by roughly 0.62, and doubling the memory squares it.

What to try

The page opens on the first probe, and it is already wrong: an id that was never inserted has landed on three bits that other ids happened to light. Press Run every probe and three of the sixteen come back present. Drag the step control back to zero and forward again to watch the array fill in bursts of three, which is where those collisions come from.

Note that this is not a misconfiguration. Four bits per id wants exactly three hash functions, which is what Use the best k picks and what the page is already set to. Drag the hash count up to twelve and the array goes almost solid; drag it down to one and collisions come back for the opposite reason. Three really is the floor, and the floor is about one false yes in seven.

So push the bits per id up instead. At ten bits the probe row goes clean at once, even with the hash count still on three — the predicted rate has fallen from fifteen per cent to 1.6, and sixteen probes are no longer enough to catch it out. Press Use the best k to move to seven and it halves again to 0.65. That is the real lever. The hash count is worth a factor of a few; the memory budget is worth a factor of 0.62 per bit, compounding.

This is why Bloom filters sit in front of expensive lookups rather than replacing them. A no ends the query immediately and is never wrong. A yes costs you the real lookup you were going to do anyway, so a false positive is a wasted trip, not a wrong answer.
