A Message Is One Number Between Zero and One

Start with the whole line from zero to one and cut it into pieces, one per symbol, each as wide as that symbol is likely. The first symbol of the message picks a piece. Now forget the rest of the line, magnify the piece you picked, and cut it up the same way for the second symbol. Keep going. The bars on the left are those magnifications stacked, and the message is any number left inside the last one.

Two things are worth noticing as you step. The interval never leaves its parent, and the pieces at every level tile it exactly with nothing spare. So a number in the final interval determines the whole message: there is only one path of cuts that could have produced it.

Why the width is the answer

width after n symbols = p(s₁) × p(s₂) × … × p(sₙ)

Each cut multiplies the width by the probability of the symbol chosen, so the final width is the probability of the exact message. Pinning down a number inside an interval of width w takes about log₂(1/w) bits, and log₂(1/w) is the sum of log₂(1/p) over the symbols — the information content of the message. The arithmetic coder does not approximate that figure. It falls out of the geometry.

The price is a constant, not a rate. One extra bit guarantees a number with that many binary places actually lands inside the interval, and the rounding up costs less than one more. Watch the readout: the coder is always between one and two bits above the information content, no matter how long the message runs, so the overhead per symbol goes to nothing.

Where Huffman loses

Huffman must give each symbol a whole number of bits. Choose the lopsided coin: A carries 0.152 bits of information and B carries 3.32, but Huffman has nowhere to put a code shorter than one bit, so it spends one bit on A and one on B — a flat one bit a symbol against an ideal of 0.469. Step through and watch the grey and the Huffman line separate by more than half a bit every symbol while the arithmetic line stays glued to grey.

The win is not immediate. The terminator and the rounding up cost about a bit and a half whatever the message, so a short message can lose: any draw carrying more than one bit a symbol of actual information does, and on a lopsided coin that means an unlucky run of the rare symbol. Set the length to four and walk the message slider and you will find several. By fourteen symbols it wins nine times in ten, and by thirty it wins every time.

Now choose four equal symbols. Every probability is a power of one half, whole numbers of bits fit perfectly, and Huffman is optimal: exactly two bits a symbol with nothing wasted. The arithmetic coder ties it and then pays its one-bit terminator, so here it comes out a single bit behind and stays there. That is the whole trade. Huffman is beaten only where the probabilities are not powers of one half, which is nearly always, and beaten badly where one symbol dominates.

Reading the number back

The codeword shown is the shortest binary fraction inside the final interval. A decoder given only those bits and the same table of probabilities repeats the cuts, at each step asking which piece the number falls in, and recovers the message symbol by symbol. It never needs the interval the encoder held — only a point inside it. That is what the last readout checks on every draw.

What to try

Set the source to the lopsided coin and run the step slider to the end: the width collapses by a factor of ten whenever a rare B lands and barely moves on a run of A. Then switch to four equal symbols without touching anything else and watch the two coder lines lock together a bit apart. Finally push the message length to fourteen on the lopsided coin and compare the two totals: the gap is roughly half a bit for every symbol in the message, and it is pure waste.
