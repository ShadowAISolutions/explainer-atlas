The grid is an array. Every outlined box holds one cache line, and a line is the smallest thing memory will sell you. Ask for a single element inside a box and the whole box arrives. With the stride at four and sixteen elements to a line, the walk reads four of the sixteen and the other twelve ride along unused, which is why the boxes come up mostly pale with a few marked cells in each.

Drag the stride up. Nothing much happens for a while, and then at sixteen the picture changes completely: one marked cell per box, every box outlined, every read a miss. That is the whole lesson. The cost of a traversal is not the number of elements it reads, it is the number of lines it drags in.

Counting the lines

Step k reads element k * s, which lives in line floor(k * s / L). For a walk of n steps the lines are a run of consecutive integers when the stride is shorter than a line, and are all different when it is not, so the count is:

lines(n, s, L) = min( n, floor((n - 1) * s / L) + 1 ) traffic per useful read = L * lines / n

Below the line length the second term wins and the traffic ratio is about s: a stride of four fetches four bytes of line for every byte you wanted. At or above the line length the first term wins, the count saturates at n, and the ratio pins at L. That is the knee in the right hand plot, and it is a corner rather than a bend, because the miss rate is min(s, L) / L and a ratio of two whole numbers cannot round off.

A formula that does not survive the simulation

The brief for this page asked to assert that the lines touched match ceil(n * s / L). That formula counts the lines the walk spans, not the lines it touches, and the two part company in both directions. Take three steps of stride three over four element lines: the walk reads elements 0, 3 and 6, which sit in lines 0, 0 and 1, so it touches two. The span formula says three. Push the stride past the line length instead and the span formula runs away to thousands while the walk still touches exactly one line per step. The page asserts the corrected expression against brute force over two hundred pairs, and exhibits the counterexample so the refutation is checked rather than merely claimed.

Why the column loop is slow

Put the stride back to one and load the column major preset. It reads exactly the same thousand elements in a different order, and against this cache the tally does not move at all: both orders miss sixty four times, once per line, because nothing is evicted before it is needed again. Order on its own is not a cost. Now pull the sets down to two and the ways down to one. The row order is untouched, and the column order goes to a miss on every single read, sixteen times the traffic, because a column step jumps a whole row and the cycle of lines it revisits is longer than the cache can hold. The page checks the multiset equality, the equal cost under a roomy cache, and the factor of sixteen under a tight one.

Where the cache runs out

Capacity is the second trap. Pull the sets down to two and the ways down to one and the walk starts missing on lines it read moments ago, because a direct mapped cache sends every line whose number agrees modulo the set count to the same shelf. Set the stride to the number of elements the whole cache holds and the miss rate goes to one and stays there however many reads you take: every access maps to the same set and evicts the one before it.

What to try

Set sixteen elements to a line and step the stride from one to sixteen, watching the traffic figure climb one unit at a time and then stop dead. Then set the stride to sixteen and type i * stride + (i % 7) into the editor: a walk that wanders about inside the line it already paid for is free, and the miss rate does not move.
