The Slower Algorithm Wins For A While

Insertion sort is quadratic and merge sort is linearithmic, so merge sort is faster. That sentence is about infinity. Below a few dozen elements it is simply wrong, which is why the sort in your standard library is both algorithms.

Insertion sort's cost depends enormously on this. Merge sort's barely moves.

Both algorithms on this page sort the same array and both are counted the same way: one unit per comparison for insertion sort, and one unit times the overhead slider for merge sort. That slider is the whole argument. Asymptotic notation deliberately throws away constant factors, and the constant factor is what decides which of these two you should actually call at size thirty.

Start with the shuffled input and walk the size slider up from two. Insertion sort's curve is a parabola and merge sort's is very nearly a straight line, so the parabola must win eventually. It does — but look where. With the overhead at three the crossing is somewhere in the dozens, not in the thousands, and every size below it is one where the quadratic algorithm is the right call.

Why the crossing moves

insertion ≈ n²/4 comparisons, merge ≤ n × ceil(log₂ n) − 2^ceil(log₂ n) + 1

The second expression is not an estimate. It is the exact worst case of a top-down merge sort, and this page checks it against every one of the 5,912 permutations of up to seven elements. Setting one cost equal to the other and solving for n gives the crossover, and because the merge term is so nearly linear the answer is roughly proportional to the overhead: double what a merge comparison costs and the crossover roughly doubles too. Drag the overhead slider and watch the marker slide.

The input matters more than the order does

Now change the input. On an array that is already sorted, insertion sort makes exactly n − 1 comparisons — it is linear, better than merge sort at every size, and there is no crossover to find. On an array that is exactly backwards it makes n(n−1)/2, the worst it can do. Merge sort moves hardly at all between those two extremes, because it splits and merges the same way whatever the data holds.

That asymmetry is worth more than the asymptotic order. Real inputs are very often nearly sorted — log files, timestamps, an array with a few new entries appended — and insertion sort's cost on nearly sorted data is close to linear. Choose the nearly sorted input and compare the four bars in the lower chart: insertion sort's bar collapses while merge sort's does not move.

What the library actually does

This is not a curiosity. Practically every production sort is a hybrid: it recurses like merge sort or quicksort down to some threshold, then hands the small pieces to insertion sort. The threshold is exactly the crossover on this page — usually between sixteen and thirty-two elements, tuned on the machine it will run on, which is why the number differs between libraries. Timsort goes further and looks for runs that are already ordered, which is the same observation about real input applied at full scale.

What to try

Set the input to shuffled and the overhead to one, the fairest possible reading for merge sort: the crossover is still not at two. Then take the overhead to eight and watch it slide past a hundred. Finally switch to already sorted at any overhead and read the crossover box: there is none, because a linear algorithm is never overtaken by a linearithmic one.
